# Explicación del tema: gestión del menú de un restaurante

Elegí un restaurante porque es un negocio cercano y fácil de explicar. La mayoría de restaurantes pequeños trabaja su carta en un cuaderno o en una hoja de cálculo, y eso trae problemas concretos: dos platos con el mismo nombre, precios que se actualizan en un lugar y no en otro, o platos que siguen apareciendo como disponibles aunque la cocina ya no los prepare. La API que desarrollé ordena esa información y deja una sola fuente de verdad para el menú.

El modelo tiene dos entidades. Categoria representa un grupo del menú, por ejemplo entradas, platos de fondo, postres o bebidas. Guarda un nombre, una descripción y un estado activo. Plato representa un producto que se vende: tiene nombre, descripción, precio, disponibilidad y una categoría. La relación es de uno a muchos. Una categoría puede tener muchos platos y cada plato pertenece a una sola categoría. En la base de datos se ve como la clave foránea CategoriaId dentro de la tabla Platos, y en las clases se ve como las propiedades de navegación Categoria.Platos y Plato.Categoria.

La base se creó primero con un script SQL que está en database/01_restaurante.sql. El script arma las tablas, los índices, la clave foránea y carga cuatro categorías con nueve platos de ejemplo. Después generé el modelo con scaffold, o sea, base de datos primero. El scaffold creó las entidades y el DbContext en la capa de Datos; luego moví Categoria y Plato al proyecto Entidades y ajusté el namespace. Las entidades no llevan [JsonIgnore]. Eso no hace falta porque la API nunca las devuelve: todas las respuestas salen como DTOs.

La solución tiene cuatro proyectos. Entidades guarda las entidades y los DTOs. Datos guarda el DbContext, las interfaces de repositorio y sus implementaciones. Negocio guarda las interfaces de servicio, los servicios, la excepción de reglas de negocio y el MappingProfile. Api guarda los controladores y el Program.cs. Las referencias van en cadena: Api hacia Negocio, Negocio hacia Datos y Datos hacia Entidades. Gracias a eso el controlador no puede usar el DbContext ni las entidades, solo los servicios por su interfaz y los DTOs.

El recorrido de una solicitud es sencillo de seguir. Por ejemplo, un GET a api/platos entra al PlatosController, que llama a IPlatoServicio. El servicio pide los datos a IPlatoRepositorio, el repositorio arma la consulta LINQ con Entity Framework, la ejecuta de forma asíncrona y devuelve entidades. El servicio las convierte a PlatoDto con AutoMapper y el controlador responde Ok con la lista de DTOs. En ningún punto del camino la entidad sale hacia el cliente.

Hay seis DTOs. CategoriaDto y PlatoDto se usan para lectura. CategoriaCrearDto, CategoriaActualizarDto, PlatoCrearDto y PlatoActualizarDto se usan para entrada y llevan Data Annotations como [Required], [StringLength] y [Range]. La separación entre crear y actualizar permite que cada operación tenga sus propias reglas. Por ejemplo, el DTO de actualización de categoría incluye Activo para poder desactivarla, mientras que el de creación no lo incluye porque toda categoría nueva nace activa.

AutoMapper se configura en un único MappingProfile dentro de la capa de Negocio. Cada mapeo tiene una dirección clara. Las entidades se convierten a DTOs de lectura porque es lo que la API devuelve. Los DTOs de entrada se convierten a entidades porque es lo que llega del cliente y se necesita guardar. Hay dos configuraciones especiales con ForMember y MapFrom. En CategoriaDto, CantidadPlatos se calcula con la cantidad de platos de la categoría. En PlatoDto, CategoriaNombre toma el nombre de la categoría relacionada en lugar de devolver el objeto completo. Esa segunda configuración es justamente la que evita el ciclo de JSON y la que hace que la respuesta sea más útil para el cliente.

No usé ReverseMap. Los DTOs de lectura tienen campos que no existen en la entidad, como CantidadPlatos y CategoriaNombre, y los DTOs de crear y actualizar tienen validaciones distintas. Un mapeo inverso automático quedaría incompleto y mezclaría responsabilidades. Prefiero declarar cada dirección de forma explícita.

Las reglas de negocio están en los servicios, no en los controladores ni en los repositorios. Son seis: no repetir el nombre de una categoría, no eliminar una categoría que tiene platos, no desactivar una categoría con platos disponibles, no crear platos en categorías inexistentes o inactivas, no mover un plato a una categoría inactiva y no repetir el nombre de un plato dentro de la misma categoría. Cuando alguna se incumple, el servicio lanza ReglaNegocioException y el controlador la convierte en un 409 Conflict con un mensaje claro.

La API tiene once endpoints. Hay CRUD completo para categorías y para platos. Los GET permiten filtros por query string: las categorías se filtran por nombre y estado; los platos por nombre, categoría, rango de precio y disponibilidad. También hay una ruta anidada, api/categorias/{categoriaId}/platos, que devuelve los platos de una categoría y responde 404 si la categoría no existe. Los códigos de respuesta se respetan: 200 para consultas correctas, 201 para creaciones con la ruta del nuevo recurso, 204 para actualizaciones y eliminaciones, 400 para datos inválidos, 404 para recursos inexistentes y 409 para reglas de negocio incumplidas.

Swagger permite ver y probar todo el contrato. En los esquemas solo aparecen los DTOs y ProblemDetails, nunca las entidades. Esa fue una de las comprobaciones importantes del laboratorio, porque demuestra que la API está exponiendo lo que debe exponer y no el modelo interno de la base de datos.
